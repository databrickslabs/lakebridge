## Prerequisites

### 1. Download
- No ODBC driver is required. The ClickHouse profiler connects over the HTTP interface using the
  [`clickhouse-connect`](https://clickhouse.com/docs/integrations/python) client, which is installed with Lakebridge.

### 2. Connectivity
- **ClickHouse Cloud**: connect on port **8443** with TLS (`secure`). The host ends in `.clickhouse.cloud`.
- **Self-managed / OSS**: connect over the HTTP interface (default port **8123**). The native protocol port (9000)
  is **not** used.

### 3. System log tables (OSS only)
System log tables must be enabled for the workload, features, dependencies, and utilization collectors to return
data. ClickHouse Cloud enables them by default; on self-managed builds ensure `query_log`, `part_log`, and
`metric_log` are configured. Some tables (e.g. `system.session_log`, `system.query_views_log`) do not exist on all
builds — the profiler records a non-fatal warning and continues, and the corresponding table is still created empty.

### 4. Required Permissions

The profiler runs **read-only** queries against `system.*` metadata and `information_schema`. It never reads user
data or modifies anything. For a dedicated profiler user:

```sql
CREATE USER profiler IDENTIFIED BY '<password>';
GRANT SELECT ON system.* TO profiler;
GRANT SELECT ON information_schema.* TO profiler;
GRANT SHOW TABLES ON *.* TO profiler;
GRANT SHOW COLUMNS ON *.* TO profiler;
GRANT SHOW DATABASES ON *.* TO profiler;
```

On ClickHouse Cloud, the built-in `default` user (or any user with the `default` role) already has the required
access.

## OSS vs Cloud (auto-detected)

ClickHouse has two profiler variants, **`oss`** and **`cloud`**, which are **detected automatically** — you do not
select one. A host ending in `.clickhouse.cloud` is treated as Cloud; otherwise the profiler reads the
`cloud_mode` server setting (`1` on Cloud, absent/`0` on self-managed). On Cloud, queries read across replicas via
`clusterAllReplicas(...)`; on OSS they read the single node.

## Profiled Collectors and Tables

The ClickHouse profiler runs seven collectors. Each collector produces several named result sets, and each result set
is written to its own DuckDB table named `<collector>_<result_set>` (for example `workload_query_volume_summary`,
`objects_tables`). Every table is always created — result sets with no rows are written as empty, typed tables so the
output schema is consistent across runs and deployments.

## Cost Attribution

The `costs` collector attributes usage across four buckets — **storage**, **compute**, **scan**, and **ingestion** —
from `system.parts` and `system.query_log`, and always reports a **resource footprint** (compressed/disk GB,
compute-weight distribution, query activity).

Dollar figures are **actual billed cost only**, never a synthetic estimate:

- On **self-managed / OSS**, no dollar figures are produced — ClickHouse Cloud metered pricing does not apply. Use the
  resource footprint to size against your own infrastructure.
- On **ClickHouse Cloud**, when Cloud API credentials are configured, the profiler reads the **actual billed cost**
  and the **plan tier** (Basic / Scale / Enterprise) from the Cloud `usageCost` API, along with the service's real
  provider/region and compute sizing. Without Cloud API credentials, the footprint and usage attribution are still
  reported, but no dollar figures.

<Admonition type="info" title="Plan tier">
    The plan tier is recorded as metadata (from the Cloud API <code>organizationTier</code>) and does not drive any
    pricing calculation. It reflects billed history and can lag a same-day plan change; set <code>tier</code> in the
    Cloud API configuration to override it.
</Admonition>

## Data Privacy and Redaction

The profiler reads only `system.*` metadata, but some fields can be sensitive (raw SQL text, authentication
parameters, host IPs/allow-lists, row-policy filters). Redaction is **on by default** and replaces those fields with
`[REDACTED]` in the output. Aggregate metrics, counts, and grant structure are always preserved. You can opt out
during configuration.

### Configuration Parameters

| Parameter | Description | Default |
|:----------|:------------|:--------|
| **Secret vault type** | `local` for plain text values, `env` to read from environment variables | — |
| **Secure (TLS)** | Use a TLS connection. Required for ClickHouse Cloud; typically `no` for local/OSS. | — |
| **Host** | ClickHouse host. A `*.clickhouse.cloud` host selects the Cloud variant automatically. | `127.0.0.1` |
| **Port** | ClickHouse HTTP port. | `8443` (secure) / `8123` |
| **User** | ClickHouse username. | `default` |
| **Password** | ClickHouse password (hidden input). | — |
| **Days back** | Lookback window (days) for query-history collectors. | `30` |
| **Redact** | Replace sensitive fields (SQL text, auth params, IPs, row-policy filters) with `[REDACTED]`. | `yes` |
| **Cloud API Key ID / Secret** | ClickHouse Cloud API key for actual billed cost, real sizing, and plan tier (Cloud only, optional). | — |
| **Organization / Service id** | Optional Cloud API scoping; auto-detected when there is exactly one. | — |
| **Tier override** | Force the plan tier (`basic`/`scale`/`enterprise`) instead of auto-detecting. | — |

## Execute the Profiler

Once configured, run the profiler to extract metadata and metrics from your ClickHouse instance:

```bash
databricks labs lakebridge execute-database-profiler --source-tech clickhouse
```

The profiler will:
1. Connect to your ClickHouse instance and auto-detect the `oss` / `cloud` variant
2. Run the seven collectors' read-only `system.*` queries
3. Store the results in a local DuckDB extract file (one table per collector result set)
