## Prerequisites

### 1. Download
- No ODBC driver is required. The ClickHouse profiler connects over the HTTP interface using the
  [`clickhouse-connect`](https://clickhouse.com/docs/integrations/python) client, which is installed with Lakebridge.

### 2. Connectivity
- **ClickHouse Cloud**: connect on port **8443** with TLS (`secure`). The host ends in `.clickhouse.cloud`.
- **Self-managed / OSS**: connect over the HTTP interface (default port **8123**). The native protocol port (9000)
  is **not** used.

### 3. System log tables (OSS only)
System log tables must be enabled for the workload, features, dependencies, and utilization collectors to return
data. ClickHouse Cloud enables them by default; on self-managed builds ensure `query_log`, `part_log`, and
`metric_log` are configured. Some tables (e.g. `system.session_log`, `system.query_views_log`) do not exist on all
builds — the profiler records a non-fatal warning and continues, and the corresponding table is still created empty.

### 4. Required Permissions

The profiler runs **read-only** queries against `system.*` metadata and `information_schema`. It never reads user
data or modifies anything. For a dedicated profiler user:

```sql
CREATE USER profiler IDENTIFIED BY '<password>';
GRANT SELECT ON system.* TO profiler;
GRANT SELECT ON information_schema.* TO profiler;
GRANT SHOW TABLES ON *.* TO profiler;
GRANT SHOW COLUMNS ON *.* TO profiler;
GRANT SHOW DATABASES ON *.* TO profiler;
```

On ClickHouse Cloud, the built-in `default` user (or any user with the `default` role) already has the required
access.

## OSS vs Cloud (auto-detected)

ClickHouse has two profiler variants, **`oss`** and **`cloud`**, which are **detected automatically** — you do not
select one. A host ending in `.clickhouse.cloud` is treated as Cloud; otherwise the profiler reads the
`cloud_mode` server setting (`1` on Cloud, absent/`0` on self-managed). On Cloud, queries read across replicas via
`clusterAllReplicas(...)`; on OSS they read the single node.

## Profiled Collectors and Tables

The ClickHouse profiler groups its extracts into seven logical collectors. Each produces several named result sets,
and each result set is a paired **DDL + SQL** profiler step: the DDL creates a typed DuckDB table named
`<collector>_<result_set>` (for example `workload_query_volume_summary`, `objects_tables`), and the SQL reads the
corresponding `system.*` data from the source. Because the table is created from explicit DDL first, its schema stays
consistent across runs and deployments even when a result set comes back empty. Steps that read per-node log tables
(`query_log`, `session_log`, `query_views_log`, `asynchronous_insert_log`) are marked optional, so a build without
those tables degrades gracefully instead of failing the run.

## Cost Attribution

The `costs` collector attributes usage across four buckets — **storage**, **compute**, **scan**, and **ingestion** —
from `system.parts` and `system.query_log`, and always reports a **resource footprint** (compressed/disk GB,
compute-weight distribution, query activity).

Dollar figures are **actual billed cost only**, never a synthetic estimate:

- On **self-managed / OSS**, no dollar figures are produced — ClickHouse Cloud metered pricing does not apply. Use the
  resource footprint to size against your own infrastructure.
- On **ClickHouse Cloud**, when Cloud API credentials are configured, the profiler reads the **actual billed cost**
  and the **plan tier** (Basic / Scale / Enterprise) from the Cloud `usageCost` API, along with the service's real
  provider/region and compute sizing. Without Cloud API credentials, the footprint and usage attribution are still
  reported, but no dollar figures.

<Admonition type="info" title="Plan tier">
    The plan tier is recorded as metadata (from the Cloud API <code>organizationTier</code>) and does not drive any
    pricing calculation. It reflects billed history and can lag a same-day plan change; set <code>tier</code> in the
    Cloud API configuration to override it.
</Admonition>

## Data Privacy and Redaction

The profiler reads only `system.*` metadata, but some fields can be sensitive (raw SQL text, authentication
parameters, host IPs/allow-lists, row-policy filters). These fields are **always redacted**: the extract SQL
selects a `[REDACTED]` literal in their place rather than the real value, so sensitive data never leaves the source.
Aggregate metrics, counts, and grant structure are always preserved. Redaction is built into the SQL and is not
configurable.

## Configure Connection to ClickHouse

Run the following command to configure the profiler connection to your ClickHouse instance:

```console
databricks labs lakebridge configure-database-profiler

Please select the source system you want to configure
...
Enter a number: <clickhouse>

(local | env)
local means values are read as plain text
env means values are read from environment variables, and fall back to plain text if not variable is not found

Enter secret vault type (local | env)
[0] env
[1] local
Enter a number between 0 and 1: 1
Use a secure (TLS) connection? (required for ClickHouse Cloud) (yes/no): yes
Enter the ClickHouse host: my-service.us-east-1.aws.clickhouse.cloud
Enter the ClickHouse HTTP port (default: 8443):
Enter the ClickHouse user (default: default):
Enter the ClickHouse password:
Configure ClickHouse Cloud API credentials for actual billed cost? (Cloud only) (yes/no): yes
Enter the Cloud API Key ID: <key-id>
Enter the Cloud API Key Secret:
Enter the Cloud organization id (optional, blank to auto-detect):
Enter the Cloud service id (optional, blank to auto-detect):
Override the plan tier? (default: auto-detect from the Cloud API) (yes/no): no
Do you want to test the connection to clickhouse? (yes/no): yes
```

### Configuration Parameters

| Parameter | Description | Default |
|:----------|:------------|:--------|
| **Secret vault type** | `local` for plain text values, `env` to read from environment variables | — |
| **Secure (TLS)** | Use a TLS connection. Required for ClickHouse Cloud; typically `no` for local/OSS. | — |
| **Host** | ClickHouse host. A `*.clickhouse.cloud` host selects the Cloud variant automatically. | `127.0.0.1` |
| **Port** | ClickHouse HTTP port. | `8443` (secure) / `8123` |
| **User** | ClickHouse username. | `default` |
| **Password** | ClickHouse password (hidden input). | — |
| **Cloud API Key ID / Secret** | ClickHouse Cloud API key for actual billed cost, real sizing, and plan tier (Cloud only, optional). | — |
| **Organization / Service id** | Optional Cloud API scoping; auto-detected when there is exactly one. | — |
| **Tier override** | Force the plan tier (`basic`/`scale`/`enterprise`) instead of auto-detecting. | — |

### Credentials File Format

`configure-database-profiler` writes the answers above to a credentials YAML at the default Lakebridge
location. You can also write this file by hand (or keep a separate one per environment and point at it
with `--cred-file-path`). The connection keys (`host`, `port`, `user`, `password`, `secure`) are flat
under the `clickhouse` block, and the optional ClickHouse Cloud API settings nest under `cloud_api`.
The query-history window is a fixed 30 days and sensitive fields are always redacted, so there are no
profiler knobs to set. The `oss` / `cloud` variant is auto-detected from the host and `secure` — there
is no variant field.

<Admonition type="warning" title="Keep secrets out of version control">
    This file holds plain-text passwords and (on Cloud) API secrets when the secret vault type is
    <code>local</code>. Store it outside your repo, restrict its permissions, and delete it when you are
    done. To avoid plain text, set the secret vault type to <code>env</code> and put the environment
    variable <em>names</em> in the file instead of the values.
</Admonition>

**Self-managed / OSS** — no TLS, no Cloud API block, no dollar figures produced:

```yaml
secret_vault_type: local
secret_vault_name: null
clickhouse:
  host: 127.0.0.1
  port: 8123
  user: <username>
  password: "<password>"       # empty string "" if the user has no password
  secure: false
```

**ClickHouse Cloud** — TLS on 8443, with the optional `cloud_api` block for actual billed cost and
plan-tier detection:

```yaml
secret_vault_type: local
secret_vault_name: null
clickhouse:
  host: <service-id>.<region>.<cloud>.clickhouse.cloud   # the *.clickhouse.cloud host selects the Cloud variant
  port: 8443
  user: default
  password: "<service-password>"
  secure: true
  # Optional: pulls actual billed cost, real compute sizing, and plan tier from the Cloud API.
  # Remove this whole block to skip it — the usage footprint and attribution are still reported,
  # just without dollar figures.
  cloud_api:
    key_id: "<CLOUD_API_KEY_ID>"
    key_secret: "<CLOUD_API_KEY_SECRET>"
    # organization_id: "<org-uuid>"   # optional; auto-detected when you have exactly one org
    # service_id: "<service-uuid>"    # optional; else matched by host
    # tier: scale                     # optional override: basic | scale | enterprise
```

<Admonition type="info" title="Cloud host, password, and API key are different things">
    The <code>host</code> and <code>password</code> are the service's SQL/HTTPS connection details (from
    the service's <strong>Connect</strong> screen in the Cloud console) — the profiler needs them to run
    the <code>system.*</code> collectors. The <code>cloud_api</code> key pair is a separate API key
    (Cloud console → <strong>API Keys</strong>) used only for the cost/tier lookup. Supplying the API key
    alone is not enough to connect.
</Admonition>

## Execute the Profiler

Once configured, run the profiler to extract metadata and metrics from your ClickHouse instance:

```bash
databricks labs lakebridge execute-database-profiler --source-tech clickhouse
```

The profiler will:
1. Connect to your ClickHouse instance and auto-detect the `oss` / `cloud` variant
2. Run the read-only `system.*` SQL steps (and, on Cloud with API credentials, the optional cost-enrichment step)
3. Store the results in a local DuckDB extract file (one table per result set)
